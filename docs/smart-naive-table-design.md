## 设计标准(用户确认,所有方案与原型必须遵守)

1. **参考 naive-ui 官方标准**:组件、props、尺寸、主题变量一律以官方为准(本地 `node_modules/naive-ui` typings / styles / 官方仓库源码),不凭记忆写;官方没有的能力明确标为「自有扩展」并说明理由。
2. **设计风格参考 macOS**:克制留白、轻分隔、次级操作降级、一屏一个主色按钮、动效克制、明暗两套。
3. **设计稿 HTML = 所见即所得的真实模拟**:用真实数据、真实操作;页面里不放用来「展示效果」的额外按钮或文字说明(如宽度切换、模式开关、档位标签、注释标注)。
   布局档位由真实容器宽度触发(缩放窗口即可看到);每个控件都真的工作。方案的解释与取舍写在本文,不写在页面上。
4. **官方优先是基线(用户 2026-09-30 再次强调)**:本库是在官方 naive-ui 之上的增强,**官方已有的功能、组件、props、实例方法、locale 文案一律直接用官方的**,不重复造。
   只有官方确实做不到的才做自有扩展,且必须写明「官方为什么做不到」。每条提议落笔前先对照本地 `node_modules/naive-ui/es` 源码,并在文档里留下出处(文件:行号)。

## 1 搜索区布局 —— 已定

两种模式共存,新增可选属性,默认行为与 v2.1.1 一致。

- **模式 1 · `search: { container: 'card' }`(默认)**:搜索表单独占一张 `n-card`,网格排布。
  代价:卡片内边距(官方 medium = 19px + 20px〔已更正(D10):无 header 的卡片内容上内边距取 `--n-padding-bottom`,2.1.1 实际是 20px + 20px,见 5.4〕)+ 卡片间距 16px 是与搜索项数量无关的恒定垂直开销。
- **模式 2 · `search: { container: 'table' }`(本期新增)**:搜索并入表格卡片,一行「字段 + 比较符 + 值」条件构造器。
  搜索区恒定占三个控件的宽度,不随可搜索字段数增长;右侧留给业务按钮与工具按钮。
  字段候选 = 列上声明了 `search` 的列(沿用列驱动,不另开配置);产出仍是现有 `FilterValue`,走现成的 `filterSerializer`。
- **兼容**:不写 `container` 默认 `'card'`;旧的「只写 `layout:'inline'`」等价 `container:'none'`,行为不变。
- **多条件面板**:同字段多条可选「且/或」(写入该字段 `FilterValue.logic`);**跨字段固定「且」**——
  `FilterState` 是按字段分键的扁平结构,跨字段 OR 需改数据模型,不在本期。
- **`FilterAction` 由 8 个扩到 15 个**,新增:`isNull` `isNotNull` `like` `startsWith` `endsWith` `in` `notIn`。
  必须同时动四处:`types.ts` 枚举 → `filter.ts` 求值 → `labels.ts` 文案 → 测试。
  〔二轮评审 D1(见 10 节)〕操作符的类型、求值、labels、序列化、无值算子常量**提前到 P0**(纯逻辑);**列头面板的默认操作符集合保持 2.1.1 的 8 个**,7 个新操作符只在宿主于列上显式写 `filter.actions` 时出现;模式 2 条件构造器(P1)默认给各类型的「推荐集合」(规格 §5.9);原「C4」改记为 A 级「新增」。
  两个已知的坑(原型里已验证过):
  - `isNull` / `isNotNull` 无值,不能按「没填」被丢掉(`isActive` 需为无值操作符放行)。
  - 比较符按字段类型分发(text / number / date / select),换字段后若当前比较符不再适用要自动重置。
- **对标准的交代**:naive-ui 官方没有「搜索表单 + 表格」页面级布局范式,卡片式布局与条件构造器都是本库自有扩展。
  多条件面板用官方 `NPopover`,对齐官方列头筛选 `{ trigger: 'click', placement: 'bottom' }`。

### 2.6 窄屏 / 手机宽度 —— 已采纳(2.12 确认)

**问题(已复现)**:原型里把卡片宽度固定为 390px(手机),模式 2 那一行:

- `.cond` 是不换行的 flex,控件为固定宽度 148 + 128 + 208,加 `»`、搜索、重置,整组 `scrollWidth = 655px`,而可用宽度只有 `340px`。
- 结果:值输入框右边缘超出内容区 159px,「搜索」超出 260px,「重置」超出 314px —— 按钮漂出卡片。
- 根因:`flex-wrap` 只在「组」之间生效,`.cond` 这一整组自己不可压缩;2.2 的「自动换行」在组内无效。
- 多条件面板同样是固定 `660px`,手机上必溢出。

(测量方法:本地起静态服务加载原型 —— Playwright 拦截 `file:` 协议 —— 把 `#preview` 设为 390px 宽后读 `getBoundingClientRect`。)

**提议**:

1. **换行粒度是「组」,不是控件**。三个组:标题 / 条件构造器 / 业务按钮+图标,各自不可拆散,避免出现孤儿按钮(如「重置」单独掉一行)。
2. **控件宽度流式**:去掉固定 208px;字段、比较符给宽度区间,值输入框 `flex: 1 1 <基准>` 且 `min-width: 0`。
3. **断点用容器查询**(`container-type: inline-size` 挂在 `.smart-table` 根),不用视口媒体查询:后台里表格常在「左树右表」的窄容器中,视口宽度不代表表格宽度。
   已知代价:模式 1 的 `n-grid responsive="screen"` 是视口口径,两者不一致,模式 1 不动。
   *(容器查询的浏览器支持度,写入实现前需核对官方兼容表,此处不凭记忆下结论。)*
4. **三档**(按卡片外宽;阈值由各控件最小宽度累加得出,原型里按 **窄 < 600 / 中 < 960 / 宽 ≥ 960** 落地,以实测为准)**〔阈值已被 2.11 取代:现行 窄 < 600 / 中 < 1280 / 宽 ≥ 1280,下面 960 / 959 与 917 的估算作废〕**:
   - 宽(≥ 960px):单行三段式(2.1)。估算:标题 64 + 条件构造器最小 539 + 业务按钮 138 + 图标 92 + 间距 36 + 卡片内边距 48 ≈ 917。
   - 中(600–959px):两行 —— 行1「标题 … 业务按钮 + 图标」,行2「字段 │ 比较符 │ 值(伸缩) │ » │ 搜索 │ 重置」(最小 539 + 内边距 48 = 587 < 600)。
   - 窄(< ~560px,手机)**〔原提议,已被下方 2.6a 取代〕**:行1「标题 … 内置图标」;行2「字段 │ 比较符」各 50%;行3「值(伸缩) │ » │ 搜索 │ 重置」;行4 折叠的「操作 ▾」。
     问题:低频的字段 / 比较符占了首屏,共 4 行。
5. **弹层不漂**〔面板宽度已被 3.9 取代:现行 `min(400px, 100vw − 16px)`〕:多条件面板宽度改 `min(660px, 100vw - 32px)`,窄档下每条件行折成两行(字段+比较符 / 值+删除);
   依赖 `NPopover` 自身的 teleport 与翻转防出屏(其 `width` / `flip` 等 props 需对照本地 d.ts 核实后再定)。
6. **同档内高度确定**:批量栏与条件构造器占同一区域时取较大高度占位(`min-height`),勾选 / 取消不让表格跳动。
   批量栏窄档下:「已选 N 项 + 取消」一行,批量按钮 wrap 到下一行。
7. ~~表格本体不用管~~ **已被用户否决(2026-09-29)**,见下方 2.7。

**验收(实现期回归测试)**:容器宽 390 / 560 / 720 / 1024 下,工具栏 `scrollWidth ≤ clientWidth`,且所有控件 `right ≤ 内容区右边界`。

### 2.6a 窄档搜索框 —— **已定**(2026-09-29,用户选「单输入框 + 筛选底部抽屉」)

原则:手机上绝大多数搜索是「敲关键词」,字段 / 比较符是低频操作,不占首屏。

- **首屏**:一个全宽值输入框(占位符带当前字段名,如「搜索 物料编码」)+ 一个「筛选」按钮(带已生效条件数角标)。
- **「筛选」**:窄档用底部抽屉展开完整条件构造器(字段 / 比较符 / 值 / 添加条件 / 重置 / 应用〔「应用」已被 3.9 取代:现行「确认」〕);宽、中档仍是 `NPopover`。

### 3.7 options 列的「勾选 ↔ 高级条件」细则 —— 已定(2026-09-30,用户授权按最佳实践;补全 3.4)

**问题(已对源码核实)**:`filter.ts:264` 的 `filterValueToOptions` 只取 `action === 'equal'` 的条件,其余**静默丢弃**,也不看 `logic`。
所以现在的勾选面板打开在 `notEqual` 或「两条 equal 且」上,会显示成「没勾选 / 勾了两个(其实语义是且)」,点确定就**覆盖原条件**——这是会丢信息的缺陷,3.4「不丢信息」规则必须靠新增判定来落实。

- **新增纯函数 `isOptionsRepresentable(value)`(放 `filter.ts`,UI 无关、可单测)**:当前过滤值能被勾选无损表达,当且仅当
  ① 所有有效条件均为 `equal` 且 `logic === 'or'`(或仅一条),或 ② 恰好一条 `in`(勾选集合 = 其数组值)。其余一律不可表达。
- **单一来源,不合并**:面板同一时刻只有一个「正在编辑的形态」。
  - 打开时:可表达 → 勾选形态;不可表达 → **自动展开「高级条件」**,原样显示原条件。
  - 勾选形态下点「高级条件」:把当前勾选**转写**成条件行(多选 → 一条 `in`)后展开,不丢选择。
  - 高级形态下收起:仅当当前草稿可表达时允许;不可表达时「收起」禁用并提示原因,用户可改到可表达,或点「重置」。
  - 提交:勾选形态写 `equal` 取「或」(与 `optionsToFilterValue` 现状一致,已发布用户的序列化输出不变);高级形态写草稿原样。
- 代价:`in` 与勾选语义等价,提交时一条 `in` 经勾选面板回写会变成若干 `equal` 取「或」——语义相同、序列化形状不同。后端若对两者有差异处理需知悉(写入 CHANGELOG)。
- 必补单测:`isOptionsRepresentable` 的各分支(含 `notEqual` / `isNull` / `and` 多 equal / 单 `in`)、回写不丢条件。

### 3.11 列宽拖拽在新表头里的落地 —— **已定**(2026-09-30,用户要求加上列宽拖拽,并连续给出「悬停才显示 / 居中压在线上 / 高度与行高一致 / 最后一列吃余量」等反馈,均已落地)

- **这是库已有能力(2.1.0)**:`resizable` 默认 `false`(opt-in)、下限 `resizeMinWidth = 60`(`config.ts:82-84`)、配合 `storageKey` 记住宽度、拖过后所有列冻结成当前宽度、并补一个占位列填满容器(`freezeWidths` / 占位列;**本节后面决定改为由最后一个数据列吸收余量,取代占位列**)。本节只讲它在 3.10 新表头里怎么与图标共存,不新增能力。原型里宿主开启 `resizable`,四个模块都有。
- **把手结构用官方、显隐有意偏离**:官方 `data-table-resize-button` 容器 8px、居中线宽 2px 高 50%,**静止时也画一条表格线色的细线**,悬停 / 拖动时变 `thIconColorActive`(`styles/_common.mjs:10-11`、`index.cssr.mjs:164-183`)。

  代价:静止时没有任何视觉提示,可发现性只靠光标变化与那条 8px 热区(与 Excel / 表格类产品的常见做法一致);触屏没有悬停,同 3.9 的已知缺口。
- **把手的位置与精致度(用户要求「设计高级一点,要居中压在线上」,并标注「要与线居中、高度与行高一致」)**:
  - **居中骑在列界线上**:热区 11px 宽,以 th 右边线为中心向两侧各出约 5px;3px 宽的主色竖条正中压在那条 1px 表格线上(实测中心偏差 0.2px)。线两侧各 5px 内都点得到把手,包括伸进下一列的那一半。
  - **高度 = 表头整行**(实测竖条 46px、表头行 45.6px,上下各外扩 1px 盖住边线,差在亚像素);拖动中再加一圈 3px 的柔和光晕(主色 18%)。
  - **拖动时一条贯穿整张表的 1px 引导线**(主色 55%),落在被拖列的右边线上,提前看到列边会落在哪;松手即消失。(Excel / Figma 一类产品的常见做法;官方没有,属自有增强。)
  - **实现约束**:骑在线上要伸进相邻列,而表头 th 原来是 `overflow:hidden` 会把它裁掉,所以表头 th 改 `overflow:visible`(标题的省略号由标题自身的容器负责),并给各列 th 依次递减的 `z-index`(靠前的列更高),否则伸进下一列的那一半会被下一列的背景盖住、也点不到。**落地到库时,这是对表头层叠的改动,要在有固定列(`fixed`)的表上再验证一次。**
- **会不会被排序箭头干扰 —— 实测结论:不会,靠四处设计避开,并留了安全距离**:
  1. **位置不重叠**:图标簇(漏斗 + 箭头)紧跟标题,**不贴右缘**;右内边距 16px = 8px 把手 + 8px 缓冲。实测默认宽度与拖到下限时,最右图标到把手左缘都稳定是 **8px**。(这也是 3.10 相对 3.8「官方漏斗贴右缘」的又一个好处:官方那个 36px 热区会和把手抢同一块地方。)
  2. **点击互不串**:把手 `data-act="noop"`,点它不会冒泡成「点表头排序」;拖动开始时收起过滤气泡(气泡锚在漏斗上,列宽一变就对不上)。
  3. **松手不误排序**:拖动结束后 150ms 内吞掉 click,否则松手落在表头上会连带触发排序。已实测:拖完立刻 click 不排序,200ms 后正常点击照常排序。
  4. **下限保护图标**:有图标的表头,拖拽下限 = `max(resizeMinWidth, 左内边距 12 + 标题 44 + 漏斗簇 30 + 箭头簇 21(可排序列)+ 右内边距 16)`,即可排序列约 123px、仅可过滤列约 102px,标题此时缩成「两个字 + 省略号」,图标完整。**库现状的下限是固定 60px,在有图标的列上会把图标挤出格子,落地时要把下限改成「取较大者」**——这是对库 `resizeMinWidth` 语义的调整(只对带图标的列抬高,其它列仍是 60)。
- **拖过列宽后的余量:由「最后一个数据列」吸收,不再补占位列(用户决定,2026-09-30:「让最后一列自动吃掉多余宽度,多一列出来看着很奇怪」)**:
  - 〔二轮评审更新(D2 / D11,见 10 节)〕下面 461、466 行的「吃余量的列不写宽度」**已被取代**:Chromium 实测,吸收列不写宽度在「拖的正是吸收列」「某列先被拖过后来成为吸收列」两种情形失效(Naive 把拖过的列记进内部 `resizableWidthsRef`,此后 `<col>` 的 width / min / max 全用拖拽值,`use-resizable.mjs`、`use-group-header.mjs:24`、`utils.mjs:38-43`、`TableParts/Header.mjs:124`,余量又被摊给所有列)。**现行规则**:吸收列 = 最后一个可见、非 fixed、`resizable !== false` 的叶子数据列(全不满足则退回最后一个数据列并写显式宽度);宿主给「操作」列写 `resizable: false` 即可退出吸收;机制见下一条〔D2 / S1 定稿〕,规格 §5.6 为准。把手高度 70%、热区 11px / 触屏 24px、拖动引导线、松手 150ms 吞 click、拖动开始收起气泡,以及 B12 后半(`th overflow:visible` + 递减 `z-index`),明确归 **P1** 视觉任务(Q-4 / Q-5);P0 只做表头图标间距 8 / 6px、右内边距 16px 与 B12 前半的下限。
  - **〔D2 / S1 定稿(2026-09-30,见 9.6)〕**:吸收列采用 **`dk` 方案**——钉住后**不写 width**、下限取声明宽 / `minWidth`(不冻结成实测宽)、`scroll-x` = Σ其余列宽 + 吸收列下限 + dragDelta(freeze 时跳过吸收列)、**永远 `resizable: false`**、新吸收列若本次挂载期间被拖过才 `tableKey++` 重挂;全部 fixed 时退路写显式宽 `max(下限, 容器 − 其余 − dragDelta)`,同样不冻结。**新代价:吸收余量的那一列没有拖拽把手**——本节原预期「最后一列仍有把手、只是拖窄不变窄」落空:向左拖它本来没有持久效果,向右只是横向撑大;要调它左侧的边界就拖左邻列的把手。**备选 `da`**(吸收列拖拽结束即 `tableKey++`,最后一列仍有把手)最终结果也对,但向左拖时其余列临时被拉宽 16–43px、松手后横向 `scrollLeft` 跳回 0(302 → 0),**被否决**。**此取舍用户可推翻**:推翻则改走 `da`,并在 CHANGELOG 注明拖拽中的抖动。规格早期的字面方案(吸收列冻结成当前渲染宽)实测在最普通的拖非吸收列就溢出 61px,已作废;决策书原预期的「钉住态下吸收列 `resizable:false`」实测更糟(首帧后把手被卸载、拖拽中断),也已作废。
  - **取代库 2.1.1 的占位列**。占位列带着表格竖线,原型里看起来像「多出一列空列」;只去掉它的右竖线(上一版修订)仍不够自然,所以改为让**最后一个数据列**不钉宽度、吸收剩余宽度。拖过之后 DOM 里的列数始终等于声明的列数,没有额外的列。
  - **冻结**:第一次按下把手,所有可见列冻结成当前渲染宽度(库的 `freezeWidths`);最后一个数据列的 `col` 不写宽度,其余列写死。〔「不写宽度」已被取代,见上〕
  - **吃余量的不能是固定在右侧的列**:官方算固定列的偏移时,没有数字宽度的固定列按 0 算(`use-scroll.mjs:34-78`,`getNumberColWidth(col) || 0`),库也因此一直给固定列补最小宽度(`useColumns.ts:286`)。所以规则是「**最后一个非固定的数据列**」;原型里「操作」代表右侧固定的操作列,因此吃余量的是「单据日期」。若所有列都固定……**已在真实 `NDataTable` 验证(2026-09-30,见 9.3):只要吃余量的那一列有数字宽度(= 容器宽 − 其余列宽之和)、`scroll-x` 取容器宽,全部列 `fixed: 'left'` 时照样填满(列宽 150 / 150 / 150 / 550,表宽 = 容器宽 1000)**;官方「没有数字宽度的固定列偏移按 0 算」只会在**不给宽度**时出问题,所以规则可以放宽为「吃余量的列永远写**显式数字宽度**」,不必再排除固定列。**真实拖拽**(边拖边重算)这一点 S3 没有覆盖,落地时仍要测。另一个重要事实见 9.3:`scroll-x` **小于**容器时,官方会把各列按比例拉伸(150 → 250),钉住的宽度不被遵守——这正是 2.1.1 要补占位列的原因,新方案里 `scroll-x` 必须始终 ≥ 容器宽。
  - **实测(Chromium,容器宽 1643)**:拖窄名称 −200 → 名称 891→691,最后一列 112→312,表宽恒等于容器宽,无横向滚动;拖宽最后一列 +150 → 312→462,表宽 1793 > 容器,出现横向滚动;再拖窄 −400 → 回落到 312(不低于填满容器);拖宽名称 +120 → 811,最后一列被压到 192。列数始终 9。
  - **已知代价(已告知并被接受)**:**最后一列拖窄时,只要总宽仍不足以填满容器,宽度不会变小**(钉住宽度只是它的最小宽度),看起来像「拖不动」——拖宽则正常。用户截图里那种「把最后一列拖窄」的操作,在原型里不会让它变窄,而是由它继续吃余量。
  - **拖拽起点取「此刻实际渲染宽度」**而不是钉住的宽度:否则最后一列(实际比钉住值宽)向右拖很久也超不过当前宽度,同样像拖不动(原型早期版本的 bug,已修)。
  - 对库的影响:2.1.1 刚发布的占位列机制(`9acc29e` / `d8dda32`)要改成「最后一个非固定数据列不写宽度」〔已被取代:吸收列的选择规则与机制见上、规格 §5.6〕;**表头 DOM 会变(不再有占位列)**,需 CHANGELOG 标注,并补回归测试:拖窄 / 拖宽 / 全部固定 / 隐藏最后一列(换下一个列当填充)四种情形。
- **不做**:双击把手重置列宽(官方无此行为,YAGNI);列宽不按模块分,同一列 key 共用一份(真实库按 `storageKey` 持久化)。
- **未验证**:真机触屏拖动(把手已设 `touch-action: none`、用 pointer 事件,理论上可行,但没在真实触屏上测过;窄档是卡片列表,本来就没有列宽拖拽)。

### 4.0 现状与两个已核实的缺陷

- 官方(本地 naive-ui 2.45.3 `use-sorter.mjs` / `interface.d.ts` 已核):列上 `sorter` 可写 `{ multiple: number, compare? }` 开启多列;
  **优先级由列声明的 `multiple` 数值决定,大者优先,与点击顺序无关**(`use-sorter.mjs:56-59`);`onUpdate:sorter` 在多列时回传 `SortState[]`;
  列有 `sortOrder`(受控)/ `defaultSortOrder`(初值)/ `customNextSortOrder`(循环顺序)。
- 库现状:`SmartTable.vue:128` 排序态是**单个** `{ field, order } | null`,`onSorterChange`(`:209-211`)遇到数组**只取 `s[0]`**。
- **缺陷 A(静默丢失)**:宿主若在列上写了 `sorter: { multiple: n }`,本地模式下 naive 自己能多列排序,但库的受控态只记第一列,
  其余列的箭头被 `useColumns.ts:453-456` 写成 `sortOrder: false`,箭头回显错乱;远程模式请求参数也只有第一列。
- **缺陷 B(默认排序被盖掉)**:`useColumns.ts:455-456` 对每个 sorter 列都写受控 `sortOrder`(初始为 `false`),而官方在存在受控列时直接返回空态
  (`use-sorter.mjs:49` `if (columnsWithControlledSortOrder.length) return []`),`defaultSortOrder` 因此不生效,远程模式也不会带默认排序去请求。
  *(**已在真实浏览器复现(2026-09-30,见 9.4)**:用库 2.1.1 现状的 `src/`(只读引用)+ 远程模式:① 列写 `defaultSortOrder: 'descend'` → 首次请求参数是 `{ page: 1, pageSize: 10 }`,没有排序参数,箭头为空;② 两列都写 `sorter: { multiple }`,依次点击 → 只有第一列有箭头,最后一次请求只有 `sortField: 'g'`,第二列被丢掉。)*

### 4.1 多列排序:支持,零新 API,**列上声明 `sorter: { multiple: n }` 才开启**(已定)

- 沿用官方写法原样透传,不另造属性;只声明 `sorter: true` / 函数的列仍是单列互斥,**已发布用户行为不变**。
- 库内排序态由「单个」升为「数组」(按优先级排好),修掉缺陷 A;单列时结构与旧行为等价。
- **优先级跟官方走(声明值),不做「按点击顺序」**:点击顺序优先级(如 AG Grid 的 Shift+点击)是另一套心智,与官方 `multiple` 冲突,且库无法覆盖官方内部排序;
  代价:用户无法自己调整「谁先谁后」,只能由宿主在列声明里定好。这是遵守「以官方为准」的直接后果。
- **远程参数**:单列时保持旧的 `{ sortField, sortOrder }` 不变;多列时**仍带**最高优先级那一列的 `sortField / sortOrder`(老后端至少拿到主排序),
  **另加** `sorts: [{ field, order }, ...]`(按优先级)。**不新增 `sortSerializer`**(官方无对应、YAGNI;真有宿主需要自定义形状再加)。

### 7.1 刷新按钮 —— **保留;静态数据模式下隐藏**(用户决定,2026-09-30)

- **决定**:刷新按钮保留在工具栏;**没有传 `fetcher`(静态数据模式)时不显示**。远程模式(传了 `fetcher`)行为不变:按当前条件和当前页重新请求(`useSmartTable.ts:88`)。
- **原因(已读源码)**:静态模式下刷新什么都不做(`SmartTable.vue:481` 直接 `Promise.resolve()`),按钮却照样显示,会误导用户。
- **已核实隐藏不会丢失任何钩子**:静态 / 远程的判定是 `isRemote = !!props.fetcher`(`SmartTable.vue:119`);`SmartTable` 对外的事件里没有 `refresh`(只有 `filterChange` / `error` / `loaded` / `columnResize` / `rowClick` / `search` / `reset` / `rowDragSort` 等),静态模式下点按钮既不发请求、也通知不到宿主。
- **落地方式**:工具栏拿到的配置里,`refresh` 取 `toolbar.refresh !== false && isRemote`;`toolbar.refresh: true` 也不能在静态模式下强行显示(显示了也是摆设)。实例方法 `refresh()` 保持导出、保持现有语义(静态模式下仍是空操作),宿主在增删改成功后调用它的用法不受影响。
- **对已发布用户的影响**:只有「静态数据 + 工具栏默认开启」的用户会少一个(本来就无效的)图标;需在 CHANGELOG 标注一句。工具栏若因此没有任何内置图标,仍按现有规则(是否还有标题 / 插槽 / 列设置)决定整条工具栏显不显示。
- **原型的宿主按远程模式模拟**:原型里的数据是内存里的 2000 行,但把它当作「远程数据源的宿主」——所以刷新按钮仍显示〔2026-10-01 已改:原型现在是真的「远程」(带延迟的 mock 后端),刷新 = 表格 loading,**没有**「已刷新」toast —— 库没有消息提示能力〕(点一下弹「已刷新」提示,没有真的重新请求)。若把原型当静态数据页,则按本条应隐藏刷新;原型不为此另做一个开关(设计标准第 3 条:页面里不放演示用的控件)。

**库不内置导出 / 导入**(已核官方源码):官方 `downloadCsv` 默认导出的是 `rawPaginatedDataRef`,即**当前页**(过滤、排序后),传 `keepOriginalData: true` 则改用原始 `props.data`、**忽略过滤**(`DataTable.mjs:102-115`);库在远程模式下手里只有当前页。另有官方 `getFilteredAndSortedData()`(`DataTable.mjs:281`,返回已过滤、已排序的**全部行**)——本地(静态)数据下宿主自己做导出时可以直接用它,但远程模式下 `NDataTable` 手里同样只有当前页。所以官方这三种出口都不等于「导出当前查询的全部结果」,这件事只有宿主(或后端)能做对;「库不内置导出」的结论不变;导入要解析文件、校验、回写,更是业务。所以库**只出菜单外壳**,不做导出 / 导入本身。

**菜单里放什么(给宿主的建议,不是库的 API)**

1. **数据进出**(原型展示):导出、导入,分隔线后「下载导入模板」。
2. 可以放:打印、复制当前页这类**低频、只读**的操作。
3. **不要放**:批量删除等破坏性操作(应在批量栏,且有二次确认);视图状态类(列显隐、密度等)——列设置已有自己的入口。
4. 排序约定:高频在前、用分隔线按类分组,破坏性的(如有)放最后。

**对已发布用户的影响**:纯新增(不传 `toolbar.more` 与 2.1.1 一致),归入 8.1 A 级。

**未验证**:① 菜单的**键盘方向键操作**——原型只保证 Tab 能到按钮、Enter 能打开,菜单内没有实现方向键,落地时依赖官方 `NDropdown` 的 `keyboard` 属性(我只确认了该属性存在,没核对默认值与实际行为);② 「批量选中时更多不显示」只读了代码(批量栏模板里没有它),没有在浏览器里点选验证;③ 原型的菜单是按官方数值**仿制**的,不是真 `NDropdown`,真实弹层的位置与边缘翻转要落地后看。

#### S1 吸收余量(`s5`,容器 1000 → 滚动容器内宽 998,每列声明宽 150)

状态机与 `SmartTable.vue` 一致:首帧 `freezeWidths`(四舍五入)→ 每帧 `dragDelta = limited − widths[key]` → 松手才 `setWidth`;钉住后 `table-layout: fixed`。吸收列 = 最后一个可见、`fixed` 为空、`resizable !== false` 的叶子列(没有时退为最后一个叶子列并写显式宽度)。

| 方案 | 含义 | 结果 |
|---|---|---|
| (a) 计划原方案 | 吸收列钉住后**不写 width**,`scroll-x` = Σ其余 + 吸收列下限 + dragDelta | 拖非吸收列通过;**拖吸收列往窄**(其余列被拉宽:A266 B266 C266 D201)、**先被拖过的列成为吸收列**(③′ A316 B316 C366;④ A458 B540)、**全 fixed 拖末列**(A354 B354 C290)失败;含 `fixed:right` 时连固定列 Op 都被拉宽(181 → 193) |
| (b) 规格 §5.6 字面 | 吸收列**也冻结成当前渲染宽**,显式 `width = max(冻结宽, 容器 − 其余)` | **最普通的拖非吸收列就失败**:D 不肯缩,D250、表宽 1060(溢出 61px)——冻结值是 Naive 未钉住时摊出的 250,成了下限 |
| (bf) | 吸收列不冻结(下限取声明宽),显式宽 | 与 (a) 的失败项相同 |
| (c) 钉住态下吸收列 `resizable:false` | 配 (a) / (bf) | **更糟**:第一次拖的正是吸收列时,首帧后把手被卸载、拖拽中断(D260、表宽 1010,`LOST`),Naive 已记下残留宽度(D242);且不处理 ④ |
| (d) 重挂:`da` / `db` | 吸收列身份变化 + 吸收列拖拽结束时 `tableKey++` | 全部情形结果正确;代价:向左拖吸收列时**拖拽中**其余列被拉宽(A 最多 +16 / +20 / +21,全 fixed 退路 +43),松手复原;每次松手重挂,横向 `scrollLeft` 302 → 0(容器 700 / 列宽 250) |
| `dy` / `bs` | `dy`:吸收列 `minWidth` = 当前填充宽;`bs`:拖拽中不重算吸收列宽 | 都在拖非吸收列时溢出约 59px(松手回正),不可取 |
| **`dk`(采用)** | (a) 的弹性吸收列 + **吸收列永远 `resizable:false`** + **仅当「新吸收列在本次挂载期间被拖过」才 `tableKey++`** | **全部情形通过**(下表) |

`dk` 关键情形(松手后列宽;括号内为 (a) 对照):

| 情形 | `dk` 结果 |
|---|---|
| ① 拖非吸收列 A +60 / −40 | A310 B250 C250 D189 表宽 998 / A210 B250 C250 D289,其余列纹丝不动(≤ 0.5px) |
| ② 拖吸收列 | 吸收列没有把手,不可拖(不存在中断问题) |
| ③′ 先拖 C +40,再隐藏 D → C 成吸收列(容器 1000 / 列宽 250) | A250 B250 C498,remounts = 1(a:A316 B316 C366) |
| ④ 拖 B +60,再隐藏 C → B 成吸收列(3 列) | A333 B665,remounts = 1(a:A458 B540) |
| ⑤ 全部 fixed,拖 A +60 | A393 B333 C272,表宽 998(退路的吸收列不冻结;冻结时 C333、表宽 1059,溢出 61) |
| ⑥ 含 `fixed:right` 的 Op,拖 A +60、B −40、隐藏 C | A332 B485 Op181,remounts = 1(a:A445 B311 Op242) |

| ⑧ 拖拽过程 | 被拖列 1:1 跟手(+60 分 6 帧 260 / 270 / 280 / 290 / 300 / 310),其余列偏差 ≤ 0.5px,吸收列实时缩放,无跳动 |

**关键源码事实**:`use-resizable.mjs:5-16` 内部 `resizableWidthsRef`,只在 `isColumnResizable(column)` 时写,且 `clearResizableWidth` 只经 `provide` 给子组件、**不在 `exposedMethods` 里**(`DataTable.mjs:269-287`)——宿主 / 库拿不到清除入口,唯一办法是重挂;`use-group-header.mjs:24` + `utils.mjs:38-43`:map 里有该 key,`<col>` 的 width / min / max 全取拖拽值,**不看 `column.width`,也不看 `column.resizable` 现在是什么**;`Header.mjs:115-124`:拖拽起点取 `getBoundingClientRect().width`,回调顺序 `onUnstableColumnResize` → `doUpdateResizableWidth`;`ResizeButton.mjs`:把手只监听 `window` 的 mousemove / mouseup,`resizable` 一变 false 把手被卸载、监听随即摘掉 = 拖拽当场中断。

**结论**:(a)(b)(c) 单独都不能通过全部情形;重挂是必需的(没有清除入口);通过全部情形的最简方案是 `dk`。**对设计的影响**:① 3.11 的「拖窄不变窄、最后一列仍可拖」预期落空——吸收列没有把手(新代价,用户可推翻,备选 `da`,见 3.11);② 规格 §5.6 字面方案作废,吸收列下限取声明宽 / `minWidth` 而不是冻结值;③ 决策书原预期的 (c) 不是解法,`resizable:false` 必须**始终**加在吸收列上。
**未测**:多级表头(`children`)下的吸收列;勾选 / 序号 / 展开等特殊列钉住态下与吸收列的联动;触屏拖拽;`minWidth` 夹紧与吸收列下限同时生效的边界;宿主传 `scroll-x` / `table-layout` 覆盖。

| 点击当下判断,卡片顶部 < 滚动容器上沿 → `card.scrollIntoView({ block: 'start', behavior: 'instant' })` | ✓ `scrollY → 316`、`cardTop → 0`;本地与远程(数据 300ms 后才回)都一样,**不必等数据回来** |
| 只在需要时滚 | 整页短(ps = 10)时 `cardTop` = 316 / 216 / 0 → 不滚;`cardTop` = −14 / −84 → 滚到 0;判据 `top < 0` 边界正确 |
| 键盘翻页(输入 3 + Enter) | ✓ `scrollY 5117 → 316` |
| 宿主内层滚动容器(`overflow:auto`,520px) | ✓ 只滚内层(`scrollTop 5365 → 300`,`window.scrollY` 始终 0);判断「是否需要滚」要先沿祖先找出实际滚动容器 |
| 宿主 `html{scroll-behavior:smooth}` | ✓ `instant` 覆盖,60ms 后已到位 |
| 宿主固定顶栏 56px | 卡片设 `scroll-margin-top:56px`、判据 `top < 56` → `cardTop → 56` ✓ |
| 远程末页变短 | ✓ |

**结论**:`fillHeight` 最小实现可行:官方 `flex-height` + `virtual-scroll` + `min-row-height`(`ceil(真实行高)`:small 40 / medium 48),根 / 卡片 / 卡片内容区 / `NDataTable` 逐层 `flex: 1 1 auto; min-height: 0`,**根元素的父容器必须有确定高度**;翻页回顶可靠,判据必须是「卡片顶部已滚出滚动容器上沿」才滚。**对设计的影响**:2.11 的 `fillHeight` 提议按此定稿(规格 §3 / §4);不开时翻页回顶写进规格 §3。**未测**:`fillHeight` 下翻页后 `scrollTo({ top: 0 })` 复位表体;横向滚动 + 虚拟滚动的表头联动;`themeOverrides` / 多行文本 / `ellipsis` 下的行高估计;Safari / Firefox;`loading` 遮罩位置。

- **场景**:`immediate: false`——进入模块时表体是官方 `NEmpty`「无数据」,**不请求**,点「搜索」才查;请求带 300–750ms 延迟(奇数页慢、偶数页快),期间表体 loading + 「搜索」按钮转圈且点击无效;**请求失败用真实业务规则触发**:单据日期范围超过 1 年 → 后端 400「请求失败(400):日期范围过大,请缩小到 1 年以内」,表格**保留旧数据**,顶部 `NMessage` 错误提示(`@error` + 宿主 message 的常见用法);快速连点翻页(第 3 页慢、随后点回第 2 页快)只认最新响应;有查询条件且无结果时用 `#empty` 插槽:「没有符合条件的单据」+「清除条件」按钮(`NEmpty` 的 extra 插槽)。

### 12.1 模块 10「行拖拽排序」(L1 L2)

- **场景**:「工序」子表(静态数据 10 行、无分页):每行左侧一个拖动手柄(`dragHandle`),拖动时被拖行浮起、其余行以 150ms 位移让位,松手后顺序真实变化、序号列跟着重排(工序号不变)并提示「已保存顺序」。窄档卡片模式**保留拖拽**:手柄放在卡片标题行左侧,触控目标 44×44,卡片间距 8 的位移同样跟随。键盘:手柄聚焦后 ↑ / ↓ 移一位。
- **实测**:把「下料」(第 1 行)拖到第 4 位 → 顺序 粗车 / 钻孔 / 铣面 / 下料 / 热处理 …,序号 1–10 连续、工序号随行(20 30 40 10 50 …);手柄聚焦按 ↑ 上移一位;窄档把「下料」卡片拖到第 3 位同样生效;拖拽全程无整表重绘(只改 transform),松手后一次重绘。
- **出处**:库 `useRowDrag.ts:41-99`(sortablejs 懒加载、`animation: 150`、`handle` 选择器、`onEnd` 里直接重排行数组并 emit `rowDragSort { from, to, reordered }`)、`SmartTable.vue:72-73、521-527`、README `row-draggable` / `drag-handle`;手柄图标 = 库 `icons.ts:34-38` 的 `DragIcon`(2×3 点阵,同列设置里的手柄)。
- **取舍(提议)**:① 原型用指针事件手写 sortablejs 的等价物(拖影 / 占位 / 位移动画),因为原型是离线单文件、不能引依赖;② **窄档规格未定**(规格 §5.8 没提卡片模式下是否保留拖拽):按设计标准选最简方案——卡片上直接保留手柄拖拽,不另开「排序模式」/ 上移下移按钮;若实现时 sortablejs 在卡片列表(非 `tbody`)上不好绑,退路是窄档隐藏手柄(另议);③ 库不自动加手柄列,宿主要自己加一列并给 `dragHandle` 选择器(原型同)。
- **库侧缺口**:① sortablejs 没有键盘排序,原型把 ↑ / ↓ 当可访问性底线做进去,库要自己补或文档写明;② 远程分页下 `rowDragSort` 只重排**当前页**的行数组、刷新即还原(库注释已写「宿主收 rowDragSort 再落库 / refresh」),文档要写明「拖拽排序适合静态数据 / 全量数据」;③ 卡片模式(P2)与拖拽的关系规格没写。
