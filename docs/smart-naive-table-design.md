## 设计标准(用户确认,所有方案与原型必须遵守)

1. **参考 naive-ui 官方标准**:组件、props、尺寸、主题变量一律以官方为准(本地 `node_modules/naive-ui` typings / styles / 官方仓库源码),不凭记忆写;官方没有的能力明确标为「自有扩展」并说明理由。
2. **设计风格参考 macOS**:克制留白、轻分隔、次级操作降级、一屏一个主色按钮、动效克制、明暗两套。
3. **设计稿 HTML = 所见即所得的真实模拟**:用真实数据、真实操作;页面里不放用来「展示效果」的额外按钮或文字说明(如宽度切换、模式开关、档位标签、注释标注)。
   布局档位由真实容器宽度触发(缩放窗口即可看到);每个控件都真的工作。方案的解释与取舍写在本文,不写在页面上。
4. **官方优先是基线(用户 2026-09-30 再次强调)**:本库是在官方 naive-ui 之上的增强,**官方已有的功能、组件、props、实例方法、locale 文案一律直接用官方的**,不重复造。
   只有官方确实做不到的才做自有扩展,且必须写明「官方为什么做不到」。每条提议落笔前先对照本地 `node_modules/naive-ui/es` 源码,并在文档里留下出处(文件:行号)。

## 1 搜索区布局 —— 已定

两种模式共存,新增可选属性,默认行为与 v2.1.1 一致。

- **模式 1 · `search: { container: 'card' }`(默认)**:搜索表单独占一张 `n-card`,网格排布。
  代价:卡片内边距(官方 medium = 19px + 20px)+ 卡片间距 16px 是与搜索项数量无关的恒定垂直开销。
- **模式 2 · `search: { container: 'table' }`(本期新增)**:搜索并入表格卡片,一行「字段 + 比较符 + 值」条件构造器。
  搜索区恒定占三个控件的宽度,不随可搜索字段数增长;右侧留给业务按钮与工具按钮。
  字段候选 = 列上声明了 `search` 的列(沿用列驱动,不另开配置);产出仍是现有 `FilterValue`,走现成的 `filterSerializer`。
- **兼容**:不写 `container` 默认 `'card'`;旧的「只写 `layout:'inline'`」等价 `container:'none'`,行为不变。
- **多条件面板**:同字段多条可选「且/或」(写入该字段 `FilterValue.logic`);**跨字段固定「且」**——
  `FilterState` 是按字段分键的扁平结构,跨字段 OR 需改数据模型,不在本期。
- **`FilterAction` 由 8 个扩到 15 个**,新增:`isNull` `isNotNull` `like` `startsWith` `endsWith` `in` `notIn`。
  必须同时动四处:`types.ts` 枚举 → `filter.ts` 求值 → `labels.ts` 文案 → 测试。
  两个已知的坑(原型里已验证过):
  - `isNull` / `isNotNull` 无值,不能按「没填」被丢掉(`isActive` 需为无值操作符放行)。
  - 比较符按字段类型分发(text / number / date / select),换字段后若当前比较符不再适用要自动重置。
- **对标准的交代**:naive-ui 官方没有「搜索表单 + 表格」页面级布局范式,卡片式布局与条件构造器都是本库自有扩展。
  多条件面板用官方 `NPopover`,对齐官方列头筛选 `{ trigger: 'click', placement: 'bottom' }`。

### 2.6 窄屏 / 手机宽度 —— 已采纳(2.12 确认)

**问题(已复现)**:原型里把卡片宽度固定为 390px(手机),模式 2 那一行:

- `.cond` 是不换行的 flex,控件为固定宽度 148 + 128 + 208,加 `»`、搜索、重置,整组 `scrollWidth = 655px`,而可用宽度只有 `340px`。
- 结果:值输入框右边缘超出内容区 159px,「搜索」超出 260px,「重置」超出 314px —— 按钮漂出卡片。
- 根因:`flex-wrap` 只在「组」之间生效,`.cond` 这一整组自己不可压缩;2.2 的「自动换行」在组内无效。
- 多条件面板同样是固定 `660px`,手机上必溢出。

(测量方法:本地起静态服务加载原型 —— Playwright 拦截 `file:` 协议 —— 把 `#preview` 设为 390px 宽后读 `getBoundingClientRect`。)

**提议**:

1. **换行粒度是「组」,不是控件**。三个组:标题 / 条件构造器 / 业务按钮+图标,各自不可拆散,避免出现孤儿按钮(如「重置」单独掉一行)。
2. **控件宽度流式**:去掉固定 208px;字段、比较符给宽度区间,值输入框 `flex: 1 1 <基准>` 且 `min-width: 0`。
3. **断点用容器查询**(`container-type: inline-size` 挂在 `.smart-table` 根),不用视口媒体查询:后台里表格常在「左树右表」的窄容器中,视口宽度不代表表格宽度。
   已知代价:模式 1 的 `n-grid responsive="screen"` 是视口口径,两者不一致,模式 1 不动。
   *(容器查询的浏览器支持度,写入实现前需核对官方兼容表,此处不凭记忆下结论。)*
4. **三档**(按卡片外宽;阈值由各控件最小宽度累加得出,原型里按 **窄 < 600 / 中 < 960 / 宽 ≥ 960** 落地,以实测为准):
   - 宽(≥ 960px):单行三段式(2.1)。估算:标题 64 + 条件构造器最小 539 + 业务按钮 138 + 图标 92 + 间距 36 + 卡片内边距 48 ≈ 917。
   - 中(600–959px):两行 —— 行1「标题 … 业务按钮 + 图标」,行2「字段 │ 比较符 │ 值(伸缩) │ » │ 搜索 │ 重置」(最小 539 + 内边距 48 = 587 < 600)。
   - 窄(< ~560px,手机)**〔原提议,已被下方 2.6a 取代〕**:行1「标题 … 内置图标」;行2「字段 │ 比较符」各 50%;行3「值(伸缩) │ » │ 搜索 │ 重置」;行4 折叠的「操作 ▾」。
     问题:低频的字段 / 比较符占了首屏,共 4 行。
5. **弹层不漂**:多条件面板宽度改 `min(660px, 100vw - 32px)`,窄档下每条件行折成两行(字段+比较符 / 值+删除);
   依赖 `NPopover` 自身的 teleport 与翻转防出屏(其 `width` / `flip` 等 props 需对照本地 d.ts 核实后再定)。
6. **同档内高度确定**:批量栏与条件构造器占同一区域时取较大高度占位(`min-height`),勾选 / 取消不让表格跳动。
   批量栏窄档下:「已选 N 项 + 取消」一行,批量按钮 wrap 到下一行。
7. ~~表格本体不用管~~ **已被用户否决(2026-09-29)**,见下方 2.7。

**验收(实现期回归测试)**:容器宽 390 / 560 / 720 / 1024 下,工具栏 `scrollWidth ≤ clientWidth`,且所有控件 `right ≤ 内容区右边界`。

### 2.6a 窄档搜索框 —— **已定**(2026-09-29,用户选「单输入框 + 筛选底部抽屉」)

原则:手机上绝大多数搜索是「敲关键词」,字段 / 比较符是低频操作,不占首屏。

- **首屏**:一个全宽值输入框(占位符带当前字段名,如「搜索 物料编码」)+ 一个「筛选」按钮(带已生效条件数角标)。
- **「筛选」**:窄档用底部抽屉展开完整条件构造器(字段 / 比较符 / 值 / 添加条件 / 重置 / 应用);宽、中档仍是 `NPopover`。
  **同一份面板内容,只换容器**,不维护两套。
- **去掉窄档的「搜索」按钮**:回车触发,输入框传 `inputProps: { enterkeyhint: 'search' }` 让键盘出现搜索键(与 2.3 一致)。
- **触控尺寸**:窄档控件用 naive 官方 `size="large"`(实测 `_common.mjs`:`heightLarge: 40px`、`fontSizeLarge: 15px`),不自造 44px / 16px。
  已知限制:40px 低于 Apple HIG 的 44pt;15px 低于 iOS Safari 聚焦自动缩放的 16px 阈值。
  这两条通行准则来自记忆、未逐条查证;按「以 naive 官方为准」不在库内 override,缩放问题归宿主页面的 viewport 设置。
- **已生效条件**以 `NTag`(`round` / `closable` / `size="small"`)展示于输入框下方,横向换行,不手写药丸样式。
- 结果:窄档从 4 行降到 **2 行**(行1「标题 … 操作 ▾ · 三个图标」,行2「输入框 + 筛选」)。
- 代价:换字段 / 比较符要多点一次「筛选」(只发生在低频路径)。
- **实现约束(设计稿落地时发现)**:布局三档可以纯 CSS(`@container`),但「气泡 vs 抽屉」是两个不同组件(`NPopover` / `NDrawer`),
  CSS 无法切换,所以库内**需要 JS 知道容器宽度**(`ResizeObserver` 或等价手段)来选容器;
  抽屉与 `NMessage` 一样 teleport 到 body,不能放进带 `container-type` 的元素里(容器会成为 `fixed` 后代的包含块)。
  此前「纯 CSS、无需测量」的说法只对布局与「操作 ▾」折叠成立,对气泡/抽屉切换不成立。
- 已核对本地 naive-ui 2.45.3 typings:`NDrawer` 的 `placement` 含 `'bottom'` 且有 `height`;
  `NInput` 有 `inputProps` / `clearable` / `onKeyup`。

### 2.7 窄档表格改为卡片式 —— 已定(细节见 2.12)

用户答复:手机宽度下「表格应该改为卡片式」(每行一张卡片,而不是保留横向滚动的表格)。

- **性质**:naive-ui `DataTable` 的 Slots 只有 `empty` / `loading`,没有卡片列表模式,这是**本库自有扩展**(需按铁律一说明理由,写入实现前对照官方 API 表再核一遍)。
- **随之丢失的入口**(卡片模式下没有表头):列头排序箭头、列头筛选漏斗、列宽拖拽、固定列、多选框列。
  其中**排序与列头筛选在手机上需要替代入口** —— 筛选可由条件构造器承担,排序需要一个独立控件。此项与模块 3、4 直接相关,不能等到最后。
- **向后兼容**:已发布库,现有用户在手机上看到的是横向滚动表格。若默认自动切卡片,等于改变既有行为,
  **默认关闭、需显式开启**(新增可选属性 `cardOnNarrow`,见 2.12)。
- **已定 · 列 → 卡片字段映射:自动推导 + 列上可选声明**。
  默认零配置:第一个数据列作卡片标题,其余列作「标签:值」两列网格,操作列放卡片底部;
  列上可选写 `card: 'title' | 'meta' | 'action' | false` 覆盖(`false` = 卡片里不显示)。
  仍是列驱动,字典 / 格式化渲染沿用,列设置里隐藏的列在卡片里同样隐藏。
  代价:自动推导未必符合业务直觉,复杂表要靠列声明调整。
- **参考对象与取舍 —— 已定(用户用「操作 ▾」方案作了改判,见下)**:用户给出 Bootstrap Blazor 文档站的移动端截图作参考
  (工具栏按钮收进一个齿轮下拉、行变「标签:值」纵排、勾选与操作各占一行)。
  - 采纳:「标签:值」纵排,操作放卡片底部(与上面映射一致)。
  - **不采纳「按钮收进齿轮」**:① 齿轮语义是「设置」,与列设置冲突;② 浮层盖住首张卡片内容(截图里「选择」行被截);
    ③ 纯图标且需两次点击,主操作被藏;④ 需要新增声明式按钮 API 才能折叠(与 2.2 的理由冲突)。
    我方原建议:手机档业务按钮保持可见、自然换行。**用户改判,见下条「已定」。**
  - **已定 · 手机档业务按钮折叠成带文字的「操作 ▾」,点开后在原位下方展开成一行(不是浮层)**(2026-09-29)。
    实现要点:`#toolbar` / `#toolbar-right` 插槽内容仍只渲染一份,不序列化;窄档下容器查询把该插槽容器默认隐藏、

- **把手结构用官方、显隐有意偏离**:官方 `data-table-resize-button` 容器 8px、居中线宽 2px 高 50%,**静止时也画一条表格线色的细线**,悬停 / 拖动时变 `thIconColorActive`(`styles/_common.mjs:10-11`、`index.cssr.mjs:164-183`)。

- **把手的位置与精致度(用户要求「设计高级一点,要居中压在线上」,并标注「要与线居中、高度与行高一致」)**:
  - **居中骑在列界线上**:热区 11px 宽,以 th 右边线为中心向两侧各出约 5px;3px 宽的主色竖条正中压在那条 1px 表格线上(实测中心偏差 0.2px)。线两侧各 5px 内都点得到把手,包括伸进下一列的那一半。
  - **高度 = 表头整行**(实测竖条 46px、表头行 45.6px,上下各外扩 1px 盖住边线,差在亚像素);拖动中再加一圈 3px 的柔和光晕(主色 18%)。
  - **拖动时一条贯穿整张表的 1px 引导线**(主色 55%),落在被拖列的右边线上,提前看到列边会落在哪;松手即消失。(Excel / Figma 一类产品的常见做法;官方没有,属自有增强。)
  - **实现约束**:骑在线上要伸进相邻列,而表头 th 原来是 `overflow:hidden` 会把它裁掉,所以表头 th 改 `overflow:visible`(标题的省略号由标题自身的容器负责),并给各列 th 依次递减的 `z-index`(靠前的列更高),否则伸进下一列的那一半会被下一列的背景盖住、也点不到。**落地到库时,这是对表头层叠的改动,要在有固定列(`fixed`)的表上再验证一次。**
- **会不会被排序箭头干扰 —— 实测结论:不会,靠四处设计避开,并留了安全距离**:
  1. **位置不重叠**:图标簇(漏斗 + 箭头)紧跟标题,**不贴右缘**;右内边距 16px = 8px 把手 + 8px 缓冲。实测默认宽度与拖到下限时,最右图标到把手左缘都稳定是 **8px**。(这也是 3.10 相对 3.8「官方漏斗贴右缘」的又一个好处:官方那个 36px 热区会和把手抢同一块地方。)
  2. **点击互不串**:把手 `data-act="noop"`,点它不会冒泡成「点表头排序」;拖动开始时收起过滤气泡(气泡锚在漏斗上,列宽一变就对不上)。
  3. **松手不误排序**:拖动结束后 150ms 内吞掉 click,否则松手落在表头上会连带触发排序。已实测:拖完立刻 click 不排序,200ms 后正常点击照常排序。
  4. **下限保护图标**:有图标的表头,拖拽下限 = `max(resizeMinWidth, 左内边距 12 + 标题 44 + 漏斗簇 30 + 箭头簇 21(可排序列)+ 右内边距 16)`,即可排序列约 123px、仅可过滤列约 102px,标题此时缩成「两个字 + 省略号」,图标完整。**库现状的下限是固定 60px,在有图标的列上会把图标挤出格子,落地时要把下限改成「取较大者」**——这是对库 `resizeMinWidth` 语义的调整(只对带图标的列抬高,其它列仍是 60)。
- **拖过列宽后的余量:由「最后一个数据列」吸收,不再补占位列(用户决定,2026-09-30:「让最后一列自动吃掉多余宽度,多一列出来看着很奇怪」)**:
  - **取代库 2.1.1 的占位列**。占位列带着表格竖线,原型里看起来像「多出一列空列」;只去掉它的右竖线(上一版修订)仍不够自然,所以改为让**最后一个数据列**不钉宽度、吸收剩余宽度。拖过之后 DOM 里的列数始终等于声明的列数,没有额外的列。
  - **冻结**:第一次按下把手,所有可见列冻结成当前渲染宽度(库的 `freezeWidths`);最后一个数据列的 `col` 不写宽度,其余列写死。
  - **吃余量的不能是固定在右侧的列**:官方算固定列的偏移时,没有数字宽度的固定列按 0 算(`use-scroll.mjs:34-78`,`getNumberColWidth(col) || 0`),库也因此一直给固定列补最小宽度(`useColumns.ts:286`)。所以规则是「**最后一个非固定的数据列**」;原型里「操作」代表右侧固定的操作列,因此吃余量的是「单据日期」。若所有列都固定……**已在真实 `NDataTable` 验证(2026-09-30,见 9.3):只要吃余量的那一列有数字宽度(= 容器宽 − 其余列宽之和)、`scroll-x` 取容器宽,全部列 `fixed: 'left'` 时照样填满(列宽 150 / 150 / 150 / 550,表宽 = 容器宽 1000)**;官方「没有数字宽度的固定列偏移按 0 算」只会在**不给宽度**时出问题,所以规则可以放宽为「吃余量的列永远写**显式数字宽度**」,不必再排除固定列。**真实拖拽**(边拖边重算)这一点 S3 没有覆盖,落地时仍要测。另一个重要事实见 9.3:`scroll-x` **小于**容器时,官方会把各列按比例拉伸(150 → 250),钉住的宽度不被遵守——这正是 2.1.1 要补占位列的原因,新方案里 `scroll-x` 必须始终 ≥ 容器宽。
  - **实测(Chromium,容器宽 1643)**:拖窄名称 −200 → 名称 891→691,最后一列 112→312,表宽恒等于容器宽,无横向滚动;拖宽最后一列 +150 → 312→462,表宽 1793 > 容器,出现横向滚动;再拖窄 −400 → 回落到 312(不低于填满容器);拖宽名称 +120 → 811,最后一列被压到 192。列数始终 9。
  - **已知代价(已告知并被接受)**:**最后一列拖窄时,只要总宽仍不足以填满容器,宽度不会变小**(钉住宽度只是它的最小宽度),看起来像「拖不动」——拖宽则正常。用户截图里那种「把最后一列拖窄」的操作,在原型里不会让它变窄,而是由它继续吃余量。
  - **拖拽起点取「此刻实际渲染宽度」**而不是钉住的宽度:否则最后一列(实际比钉住值宽)向右拖很久也超不过当前宽度,同样像拖不动(原型早期版本的 bug,已修)。
  - 对库的影响:2.1.1 刚发布的占位列机制(`9acc29e` / `d8dda32`)要改成「最后一个非固定数据列不写宽度」;**表头 DOM 会变(不再有占位列)**,需 CHANGELOG 标注,并补回归测试:拖窄 / 拖宽 / 全部固定 / 隐藏最后一列(换下一个列当填充)四种情形。
- **不做**:双击把手重置列宽(官方无此行为,YAGNI);列宽不按模块分,同一列 key 共用一份(真实库按 `storageKey` 持久化)。
- **未验证**:真机触屏拖动(把手已设 `touch-action: none`、用 pointer 事件,理论上可行,但没在真实触屏上测过;窄档是卡片列表,本来就没有列宽拖拽)。

## 4 排序 —— 已定(2026-09-30,4.1–4.7 由用户「按建议执行」采纳)

### 4.0 现状与两个已核实的缺陷

- 官方(本地 naive-ui 2.45.3 `use-sorter.mjs` / `interface.d.ts` 已核):列上 `sorter` 可写 `{ multiple: number, compare? }` 开启多列;
  **优先级由列声明的 `multiple` 数值决定,大者优先,与点击顺序无关**(`use-sorter.mjs:48-52`);`onUpdate:sorter` 在多列时回传 `SortState[]`;
  列有 `sortOrder`(受控)/ `defaultSortOrder`(初值)/ `customNextSortOrder`(循环顺序)。
- 库现状:`SmartTable.vue:128` 排序态是**单个** `{ field, order } | null`,`onSorterChange`(`:209-211`)遇到数组**只取 `s[0]`**。
- **缺陷 A(静默丢失)**:宿主若在列上写了 `sorter: { multiple: n }`,本地模式下 naive 自己能多列排序,但库的受控态只记第一列,
  其余列的箭头被 `useColumns.ts:453-456` 写成 `sortOrder: false`,箭头回显错乱;远程模式请求参数也只有第一列。
- **缺陷 B(默认排序被盖掉)**:`useColumns.ts:455-456` 对每个 sorter 列都写受控 `sortOrder`(初始为 `false`),而官方在存在受控列时直接返回空态
  (`use-sorter.mjs:44` `if (columnsWithControlledSortOrder.length) return []`),`defaultSortOrder` 因此不生效,远程模式也不会带默认排序去请求。
  *(**已在真实浏览器复现(2026-09-30,见 9.4)**:用库 2.1.1 现状的 `src/`(只读引用)+ 远程模式:① 列写 `defaultSortOrder: 'descend'` → 首次请求参数是 `{ page: 1, pageSize: 10 }`,没有排序参数,箭头为空;② 两列都写 `sorter: { multiple }`,依次点击 → 只有第一列有箭头,最后一次请求只有 `sortField: 'g'`,第二列被丢掉。)*

### 4.1 多列排序:支持,零新 API,**列上声明 `sorter: { multiple: n }` 才开启**(已定)

- 沿用官方写法原样透传,不另造属性;只声明 `sorter: true` / 函数的列仍是单列互斥,**已发布用户行为不变**。
- 库内排序态由「单个」升为「数组」(按优先级排好),修掉缺陷 A;单列时结构与旧行为等价。
- **优先级跟官方走(声明值),不做「按点击顺序」**:点击顺序优先级(如 AG Grid 的 Shift+点击)是另一套心智,与官方 `multiple` 冲突,且库无法覆盖官方内部排序;
  代价:用户无法自己调整「谁先谁后」,只能由宿主在列声明里定好。这是遵守「以官方为准」的直接后果。
- **远程参数**:单列时保持旧的 `{ sortField, sortOrder }` 不变;多列时**仍带**最高优先级那一列的 `sortField / sortOrder`(老后端至少拿到主排序),
  **另加** `sorts: [{ field, order }, ...]`(按优先级)。**不新增 `sortSerializer`**(官方无对应、YAGNI;真有宿主需要自定义形状再加)。

### 4.2 优先级展示(已定)

  若原型实测发现用户看不懂多列先后,再用官方 `renderSorterIcon` 钩子(闭包里按库的排序数组取下标)增强,而不是另造排序面板。
- 桌面不新增排序面板:官方箭头已足够。

### 4.3 表头里排序与过滤共存(已定,**被 3.10 取代**)

- **恢复默认**:桌面不新增按钮(已有代价如上);窄档排序抽屉(4.5)里的「重置」= 恢复列声明的默认排序(无默认则清空),
  与 3.3「面板『重置』= 恢复 `defaultValue`」语义一致。

### 4.5 手机 / 卡片模式的排序入口(已定,2.7 遗留)

- 窄档排序抽屉的提交 / 重置按钮文案同样取官方 locale(确认 / 重置),见 3.8。

## 5 表格密度 —— 默认值与工具栏按钮均已定(2026-09-30)

### 5.2 工具栏去掉「密度」按钮,密度交给宿主的个人设置 —— **已定**(用户决定,2026-09-30,即原备选 B)

- **决定**:表格工具栏**不再提供密度按钮**;密度是个人偏好,由宿主后台的「个人设置」决定,经 `defaultDensity`(或全局默认)传给表格。工具栏内置图标由三个减为两个(刷新、列设置),原型四个模块已是如此;窄档第 1 行的标题区因此多出约 40px(实测 113 → 153px)。
  理由:密度是「设一次就不再动」的偏好(没有使用数据,是经验判断);占一个图标位;默认改紧凑后更没理由常驻;放进个人设置,**同一个用户在所有表格上的密度一致**,而不是每张表各切各的。
- **取代**第 2 节「现状」里「三个内置按钮」的描述;`density` 图标与 `toolbar.density` 的语义随之改变(见下)。

**去掉按钮后必须同时处理的三件事(已对源码核实,否则「个人设置」会不生效)**

1. **存储里的旧密度不能再盖过宿主的值**。现状:`useColumns.ts:251` 是 `ref(stored?.density ?? opts.defaultDensity)`,存储(`storageKey` 对应的 localStorage,`storage.ts`)优先于 `defaultDensity`。
   以前点过按钮切到舒适的用户,会永远读到自己存的那份,宿主的个人设置对他们**不生效**,而他们又没有按钮可以改回来。
   **规则改为:没有密度按钮时,忽略存储里的 density,直接取宿主给的值**(存储格式的 `density` 字段保留并继续写入,只是读取时不采用,避免动 `VERSION`,旧版本库读新数据也不出错)。只有宿主显式打开密度按钮(见 3)时,才沿用「存储优先」。
2. **宿主的值要能跟随变化**。现状:`defaultDensity` 与 `provide` 的全局 `density` 都只在初始化读一次(`SmartTable.vue:197`、`config.ts` 的 `resolveDefaults` 在 setup 内合并),个人设置如果异步加载或在别处改了,已挂载的表格不会变。
   **规则**:实例上的 `defaultDensity` 改为响应式(宿主传 `:default-density="settings.density"`,变了就跟着变);全局 `provide` 的值保持「一次性」,文档写明它适合在应用启动、读完个人设置后再 `provide`。名字里的「default」此时已不准确(没有按钮后它就是当前值),但**为兼容已发布用户不改名**,文档里说明。
3. **`toolbar.density` 保留但默认改为 `false`**:已发布用户的类型里有这个键(`types.ts:228`),直接删会让传了它的宿主类型报错;labels 里的 `density` / `densityComfortable` / `densityCompact` 文案键同理保留。`toolbar: { density: true }` 仍可把按钮请回来,此时按旧规则「存储优先」。**彻底删除留到下一个 major**。

**对已发布用户的影响(CHANGELOG 必须标注)**:工具栏默认少一个图标;用户无法再在表格里切换密度;默认值由舒适变紧凑(5.1);显式写了 `toolbar.density: true` 的宿主不受影响。三处合起来是一次**默认行为变更**,建议与分页默认值(2.11)、5.1 一并按破坏性变更评估是否升 major。

**验证**:原型四个模块的工具栏均只有「刷新、列设置」,批量栏同;默认 `compact`;宽 / 窄档无溢出、控制台无报错。**未验证**:库内「忽略存储密度」与「`defaultDensity` 响应式」两条规则(尚未实现,落地时需补测试:存过 `comfortable` 的旧数据 + 宿主给 `compact` → 取 `compact`;宿主值中途变化 → 表格跟随;`toolbar.density: true` 时仍存储优先)。

### 5.3 窄档卡片固定舒适间距 + 触控目标统一 44px —— **已定**(用户决定,2026-09-30)

- **决定(三条,用户定)**:
  1. **窄档卡片固定用舒适间距,不响应密度**(卡片上下内边距 12px、卡片间距 8px);密度只作用于表格。作废 2.9 第 6 条。原型已删卡片的紧凑样式与 `vsCardEst` 的紧凑分支。
  2. **勾选框可点区域扩到 44×44px**,外观不变(仍是官方 `large` 的 18px),只加不可见热区;热区向卡片内侧留 2~3px,不伸出卡片外。
  3. **「编辑 / 删除」按钮统一为 44×44px**(原 44×40,「删除」还多了右内边距变成 56 宽)。所有触控目标统一 44px;代价是每张卡片高 4px(191 → 195px)。

## 6 分页 —— 所有宽度统一用官方 `simple` 简洁模式(用户决定,2026-09-30)

- **过程**:先因窄档「信息太多、折成两行」把手机宽度改成简洁模式;用户随后给了桌面截图,**红框圈住「上一页 + 页码序列 + 下一页」**,并附官方简单分页的示意图(`‹ [2] / 100 ›`),要求桌面也这样——即**所有宽度都用简洁模式**。
- **方案:全部宽度用官方 `NPagination` 的 `simple` 模式**(`pagination/src/Pagination.mjs` 的 simple 分支,本地 2.45.3 已核):
  - **宽 / 中档**:`共 2000 条  ‹  [页码输入框] / 20  ›  100 / 页`。总条数 prefix 与每页条数选择器**保留**(它们在红框之外,用户没要求去掉),只把红框里的页码序列换成「输入框 / 总页数」。
  - **窄档(容器 < 600)**:去掉每页条数选择器,**保留总条数**(用户要求手机上也要显示):`共 2000 条(靠左)  ‹ [页码] / 20 ›(靠右)` 单行,40px 触控尺寸。实测 360 宽、总条数长到 7 位(`共 2000000 条`)时整行高度仍是 40px、无溢出。
- **官方 simple 的行为**:输入框宽 60px(`pagination/styles/_common.mjs` `inputWidth*`),输入页码回车 / 失焦跳转(`handleQuickJumperChange`),输入框始终显示当前页。**原型实测**(Chromium,暗色):上一页 / 下一页;输入 12 → 跳到第 12 页;改每页 500 后总页数变 4、当前页夹取;输入 999 → 夹到最后一页;非法输入 / 同页 → 还原成当前页;最后一页「下一页」禁用;宽档输入框与按钮同高(28px);390 宽四个模块均为单行 40px、无溢出。
- **更正(真实 `NPagination` 实测,2026-09-30,见 9.1)**:官方 `simple` 模式**不渲染每页条数选择器,也不渲染快速跳页**——`Pagination.mjs:665` `!simple && showSizePicker`、`:682` `!simple && showQuickJumper`。上面「保留每页条数选择器」在原型里成立,是因为原型自己画了一个;**落地时库要自己用官方 `NSelect` 做,放进 `NPagination` 的官方 `suffix` 插槽**(已验证:`pagination.suffix` 渲染出「100 / 页」,分页条 28px 高,DOM 顺序为 prefix · 上一页 · 输入框 · 下一页 · suffix)。`pageSizes` / `showSizePicker` 这两个官方属性在 `simple` 下不再生效,库要在文档里写明,并由库自己把它们映射成 `suffix` 里的 `NSelect`。窄档「去掉 size picker」因此不需要任何处理(`simple` 本来就没有),只需窄档不提供 `suffix`。
- **代价**:**看不到页码序列,不能一眼「点第 3 页」**,只能翻页或输入页码;省略号悬停的快速跳页菜单也随之没有(官方 `showQuickJumpDropdown` 只在非 simple 时有)。这是用户明确要的取舍——信息更少、更干净。
- **对库的影响**:
  - 库目前没有给 `NPagination` 传 `simple`,**默认行为变更**(所有宽度的分页外观都变了),要在 CHANGELOG 标注,并与「默认每页 100 条」(2.11)、密度默认紧凑(5.1)一并评估是否升 major。落地方式建议:新增可选属性(如 `pagination.simple`),**新默认开启**;宿主传 `simple: false` 可回到页码序列。
  - 窄档去掉 size picker 需要 JS 知道窄档(库已因抽屉 / 气泡切换需要 `ResizeObserver`,见 2.6a);总条数 prefix 各档都保留(由宿主的 `#pagination-prefix` 插槽提供,库默认没有)。
  - **原型已删除**页码序列、省略号、悬停页码菜单、`pageSlot` / `pageSlotNarrow` / `showQuickJumper` 配置相关的代码与样式(simple 自带页码输入)。

## 7 工具栏:放大(页面内最大化)、刷新与更多 —— 放大已做原型,刷新保留且静态模式隐藏,更多菜单已做原型(2026-09-30)

### 7.1 刷新按钮 —— **保留;静态数据模式下隐藏**(用户决定,2026-09-30)

- **决定**:刷新按钮保留在工具栏;**没有传 `fetcher`(静态数据模式)时不显示**。远程模式(传了 `fetcher`)行为不变:按当前条件和当前页重新请求(`useSmartTable.ts:88`)。
- **原因(已读源码)**:静态模式下刷新什么都不做(`SmartTable.vue:481` 直接 `Promise.resolve()`),按钮却照样显示,会误导用户。
- **已核实隐藏不会丢失任何钩子**:静态 / 远程的判定是 `isRemote = !!props.fetcher`(`SmartTable.vue:119`);`SmartTable` 对外的事件里没有 `refresh`(只有 `filterChange` / `error` / `loaded` / `columnResize` / `rowClick` / `search` / `reset` / `rowDragSort` 等),静态模式下点按钮既不发请求、也通知不到宿主。
- **落地方式**:工具栏拿到的配置里,`refresh` 取 `toolbar.refresh !== false && isRemote`;`toolbar.refresh: true` 也不能在静态模式下强行显示(显示了也是摆设)。实例方法 `refresh()` 保持导出、保持现有语义(静态模式下仍是空操作),宿主在增删改成功后调用它的用法不受影响。
- **对已发布用户的影响**:只有「静态数据 + 工具栏默认开启」的用户会少一个(本来就无效的)图标;需在 CHANGELOG 标注一句。工具栏若因此没有任何内置图标,仍按现有规则(是否还有标题 / 插槽 / 列设置)决定整条工具栏显不显示。
- **原型的宿主按远程模式模拟**:原型里的数据是内存里的 2000 行,但把它当作「远程数据源的宿主」——所以刷新按钮仍显示(点一下弹「已刷新」提示,没有真的重新请求)。若把原型当静态数据页,则按本条应隐藏刷新;原型不为此另做一个开关(设计标准第 3 条:页面里不放演示用的控件)。

### 7.2 放大 —— **已做原型;`toolbar.maximize` 默认关闭**(2026-09-30,按建议采纳)

- **它是什么**(用户给了自己系统的两张截图):表格组件在页面内最大化,**盖住宿主的侧栏、顶栏、标签页,以及页面里的其它表格**,占满浏览器页面区域;**不调用浏览器全屏 API**(浏览器地址栏、书签栏仍在)。图标在「放大」与「还原」(收起箭头)之间切换;同页多张表各自有自己的按钮。

| 项 | 结果 |
|---|---|
| 宿主祖先带 `transform` | `Teleport to="body"` 后放大层 `0,0,1200×800`,**盖满视口**(风险 1 的解法成立) |

1. **宿主祖先带 `transform` / `filter` / `contain` 时,`position: fixed` 的包含块会变成那个祖先**,放大层就盖不住整个视口(后台布局做路由切换动画时常见)。库要用 **Vue `Teleport` 到 `body`**(`disabled` 随放大态切换,组件实例和状态保留,只搬 DOM);要验证搬动后滚动位置、虚拟滚动、`ResizeObserver` 是否正常。
2. **层级**:放大层 `z-index` 取 1999 是假设宿主顶栏 / 侧栏的 `z-index` 低于它;若宿主有更高的固定层,需要提供配置项。**我没有核对你们宿主布局的实际 z-index**,落地前要看一下。
3. **背景滚动锁定**:放大后宿主页面不应跟着滚(原型页面本身无整页滚动,没有覆盖到这一点)。
4. **焦点管理**:放大后是否把 Tab 焦点限制在放大层内(陷阱)、退出后焦点回到哪里,原型只做了「还给按钮」。
5. **模块 1 的独立搜索卡片**:原型里整个组件(搜索卡片 + 表格卡片)一起放大,搜索卡片仍在顶部;若你希望放大时隐藏搜索卡片、腾出更多行,要另议。
6. **两张表同页**:一次只应有一张处于放大态;放大某一张时另一张的按钮被盖住,不需要额外处理,但要确认宿主把它们放在同一个 Teleport 目标下不会互相抢层级。
- 这是**自有扩展**(官方 DataTable 没有全屏 / 最大化能力,已搜源码确认)。

**库不内置导出 / 导入**(已核官方源码):官方 `downloadCsv` 默认导出的是 `rawPaginatedDataRef`,即**当前页**(过滤、排序后),传 `keepOriginalData: true` 则改用原始 `props.data`、**忽略过滤**(`DataTable.mjs:102-115`);库在远程模式下手里只有当前页。两种语义都不等于「导出当前查询的全部结果」,这件事只有宿主(或后端)能做对;导入要解析文件、校验、回写,更是业务。所以库**只出菜单外壳**,不做导出 / 导入本身。

**菜单里放什么(给宿主的建议,不是库的 API)**

1. **数据进出**(原型展示):导出、导入,分隔线后「下载导入模板」。
2. 可以放:打印、复制当前页这类**低频、只读**的操作。
3. **不要放**:批量删除等破坏性操作(应在批量栏,且有二次确认);视图状态类(列显隐、密度等)——列设置已有自己的入口。
4. 排序约定:高频在前、用分隔线按类分组,破坏性的(如有)放最后。

**对已发布用户的影响**:纯新增(不传 `toolbar.more` 与 2.1.1 一致),归入 8.1 A 级。

**原型实测(Chromium,已看明暗两套截图)**:四个模块、宽 / 中 / 窄(1440 / 900 / 390)都有「更多」,菜单项为「导出 / 导入 / ── / 下载导入模板」;选中项后菜单收起并弹提示;点外部、Esc 都收起;放大态下菜单盖在放大层之上、点击命中正确、选中后仍是放大态;窄档菜单不越出屏幕、无横向滚动;窄档「新增」与「更多」宽度 163 / 161px(差 2px 是边框);控制台无报错。

**未验证**:① 菜单的**键盘方向键操作**——原型只保证 Tab 能到按钮、Enter 能打开,菜单内没有实现方向键,落地时依赖官方 `NDropdown` 的 `keyboard` 属性(我只确认了该属性存在,没核对默认值与实际行为);② 「批量选中时更多不显示」只读了代码(批量栏模板里没有它),没有在浏览器里点选验证;③ 原型的菜单是按官方数值**仿制**的,不是真 `NDropdown`,真实弹层的位置与边缘翻转要落地后看。
